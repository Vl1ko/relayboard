# Хранение вложений

## Действующая политика следующей версии

Вложения завершённых или остановленных **разовых** публикаций становятся недоступны спустя 30 суток после завершения. Проверка выполняется API раз в минуту, физическое удаление идёт ограниченными пакетами. Метаданные файлов, текст публикации и история доставок остаются.

Регулярные публикации (включая остановленные), активные, отложенные и приостановленные задания сохраняют файлы. Очистка также пропускает queued/sending/paused/unknown доставки и неопределённые или выполняющиеся WhatsApp receipts. Возобновление/ручная попытка до истечения срока начинает новый полный срок после окончания попытки. После истечения срока повтор с прежними вложениями запрещён: нужно создать новую публикацию и загрузить файлы снова. Текстовые публикации без вложений эта политика не ограничивает.

Настройки:

```dotenv
ATTACHMENT_RETENTION_DAYS=30
STORAGE_MAINTENANCE_INTERVAL_MS=60000
```

`finished_at` отражает переход в завершённое состояние и последнюю попытку доставки, а не изменение текста/получателей или время создания файла. При первой миграции старым завершённым публикациям предоставляется полный срок в 30 суток с момента миграции: точной даты завершения в прежней схеме нет. Повторная миграция дату не сдвигает.

## Надёжность удаления

Пометка об истечении срока и задания `attachment_cleanup_jobs` сохраняются одной транзакцией. Очистка выполняется только из API с доступом на запись к uploads. Несколько API-процессов используют блокировки строк; один процесс не запускает параллельные проходы.

Очередь также обслуживает явное удаление вложения/публикации: DB-trigger сохраняет задание даже при каскадном удалении. Отсутствующий файл считается успешно удалённым. Ошибка файловой системы оставляет задание с `last_error`, числом попыток и следующей датой повтора. После удаления файла и падения до подтверждения повтор безопасен.

Сборщик не обходит дерево диска, не следует symlink и не удаляет файл с действующей ссылкой в attachments. Он принимает только обычные файлы непосредственно в настроенном UPLOAD_DIR. При изменении UPLOAD_DIR необходимо согласованно перенести файлы и пути в БД/очереди, иначе задания старого корня останутся с ошибкой вместо удаления произвольных путей.

Состояния отправок и очистка сериализуются блокировкой родительской публикации. Ограничения в БД защищают также от повторов из старых процессов. Удалить публикацию во время `sending` нельзя. Неопределённый исход не разрешается автоматически ради очистки.

Скачивание истёкшего вложения возвращает HTTP 410, попытка повторить отправку — HTTP 409. Интерфейс сообщает об истечении срока и отключает кнопку ручного повтора. Сообщение об истечении срока означает недоступность файла, а не гарантию, что файловая система уже подтвердила unlink.

## Проверка перед выпуском

Сначала применить совместимую миграцию на копии БД и сделать согласованную резервную копию БД и uploads. Убедиться, что все контейнеры нового релиза содержат актуальную схему/код и используют один uploads volume. Не выкатывать целиком незавершённые изменения других функций вместе с этой задачей без отдельной проверки.

Предпросмотр без удаления (после миграции):

```bash
npm run storage:preview
# В собранном контейнере, если TypeScript-инструменты отсутствуют:
docker compose exec -T api node dist-node/api/storage-preview.js
```

Предпросмотр показывает число публикаций/файлов, логический объём и количество ожидающих заданий удаления. На старой установке сразу после миграции ожидается ноль просроченных файлов из-за полного переходного срока.

Наблюдение за неудачной очисткой:

```sql
SELECT count(*), min(created_at), max(attempts)
FROM attachment_cleanup_jobs;
SELECT storage_path, attempts, next_attempt_at, last_error
FROM attachment_cleanup_jobs WHERE last_error IS NOT NULL
ORDER BY created_at LIMIT 20;
```

Интеграционные тесты используют только отдельную БД с именем `attachment_retention_test`, создают собственную временную схему/каталог и удаляют их после проверки:

```bash
RETENTION_TEST_DATABASE_URL=postgresql://localhost/attachment_retention_test \
  node --import tsx --test src/core/attachment-retention.test.ts
```

Нельзя откатить физическое удаление одной сменой параметра или образа; для восстановления нужны согласованные backup БД/файлов. Откат кода после миграции также должен учитывать ограничения в БД. Политика пока не развёрнута на рабочем VPS.
