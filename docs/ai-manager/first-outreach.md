# E04: настройки и предпросмотр первого обращения

Инкремент от 13 ноября 2026; основание — TZ-2.3/2.4 и ответ пользователя: одна заявка определяется как контакт + отдельная явно созданная заявка. Это первая часть E04; запуск, расписание, pause/stop/resume и реальный transport ещё не реализованы.

## Реализация и зависимости

1. `database/ai-manager-outreach.sql` — миграция v3: `ai_requests` с явным UUID и связью с контактом; единственная строка настроек с версией, текстом, интервалом, упорядоченными каналами и разрешёнными аккаунтами. V1/V2 не изменяются; runner применяет v3 под прежней общей блокировкой.
2. `src/core/outreach.ts` — сохранение с optimistic revision check, идемпотентное создание заявки, read-only repeatable-read предпросмотр. `src/core/outreach.test.ts` — отдельная PostgreSQL БД `relayboard_outreach_test`, новые схемы на каждый прогон; 10 проверок данных, конкуренции и HTTP.
3. `src/api/outreach-router.ts` → server: авторизованные `/api/ai/outreach/settings` GET/PUT, `/requests` GET/POST, `/preview` POST; no-store, безопасные ошибки. Используется тот же явно выключенный по умолчанию флаг `CONTACT_IMPORT_ENABLED`, поскольку это локальное расширение раздела контактов, а не live sender.
4. `web/src/OutreachPanel.tsx` → ContactsImport: сохранение, явная новая заявка и выбор заявок для предпросмотра. Обновление списка контактов/заявок — отдельная кнопка. Форма пока показывает первые 100 контактов/последние 100 заявок; полноценный поиск/пагинация здесь ещё не реализованы.

Шаблон — буквальный текст до 4000 символов, без выполнения выражений/подстановок. Пустой шаблон сохраняется как черновик, но блокирует предпросмотр. Интервал 1–86400 секунд — инженерный диапазон; его сохранение ещё не доказывает соблюдение интервала отправками. Приоритет каналов задаётся явно, внутри канала учитывается сохранённый порядок аккаунтов, затем стабильный ID диалога. Изменение настроек не переписывает уже созданный outbox.

## Заявка и ограничения

POST requests принимает `{id, contactId}`. При потерянном ответе клиент повторяет тот же UUID; привязку существующего UUID к другому контакту изменить нельзя. Нажатие «Создать отдельную заявку» после успешного создания — отдельное осознанное бизнес-действие. Импорт не создаёт заявки. Для дальнейшего первого обращения зарезервирован logical key `request:<UUID>`; это конвенция этого workflow, не новая гарантия произвольного низкоуровневого enqueue E02.

Предпросмотр принимает `{revision, requestIds}` (1–100 уникальных заявок). На одном снимке БД проверяются шаблон, контакт, opt-out, любые записанные first_message по тому же ключу, ручные/закрытые связанные диалоги, доступность аккаунтов и явно включённый auto. Человеческое вмешательство блокирует обход через другой канал, даже если его аккаунт не входит в allowlist или удалён из legacy integrations. Два выбранных запроса к одному контакту одновременно не получают два готовых маршрута. Новый контакт без подтверждённого канального диалога не считается доступным получателем.

Ответ содержит фактический текст, интервал, маршрут или причину блокировки для каждой заявки и всегда `canStart:false`. Он не создаёт outbox, не переключает режим, не посылает сообщения, не подтверждает доставку. Снимок не является разрешением отправки: будущий runner обязан повторно проверить все guards на границе send, подтвердить ревизию и создать операцию атомарно по contact/request, а не доверять данным браузера. Unknown и любые старые операции не дают автоматического fallback. Определение «доступен сейчас» здесь — локальное состояние, не live проверка регистрации телефона.

## Миграция, совместимость, откат

Последовательность для проверочного стенда: резервная копия → базовая схема → `node --import tsx src/api/migrate-ai-manager.ts` → проверка v3/checksum → API/UI с флагом → синтетический предпросмотр. Старая версия приложения игнорирует добавленные таблицы; новая при отсутствии v3 возвращает 503. Автомиграции при запуске сервера нет.

Откат приложения: выключить флаг и вернуть предыдущую сборку; additive-таблицы и заявки оставить. Удаление таблиц не является штатным откатом: оно разрушит будущую бизнес-дедупликацию. Срок удаления заявок пока не согласован (O-09). Production-выпуск не выполнялся и этим документом не разрешается.

## Приёмка инкремента и остаток E04

Проверки нового модуля: конкурентные редакторы, рестарт, idempotent request/rebind conflict, пустой текст/старая версия, ноль отправок/смен режима, opt-out/manual вне allowlist, unknown, paused/auth/disabled, отсутствующая заявка, две заявки одного контакта, приоритет/пустой allowlist, HTTP auth/disabled/validation. Фактически выполненные проверки и сборки указаны в progress.md.

Остаются: атомарный запуск и очередь, актуальный шаблон для не начатых обращений, durable rate limit по фактическому start, pause/stop/resume, восстановление после рестарта, видимые состояния отправок, реальные адаптеры и испытания на PostgreSQL16. Выбор ИИ не нужен для этой части; поручение на реальные данные и разрешённые тестовые аккаунты по-прежнему отсутствуют. Для live send применяются gates E01/O-03/O-04.
