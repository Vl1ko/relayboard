Проверка Compose на отдельной папке с вымышленным .env:8 synthetic /9 live services, у всех одинаковый предел; контейнеры не запускались.

BullMQ получает общий fallback: completed до2000 записей/суток, failed до2000/7 дней; существующие fanout и dispatch переопределяют count до1000 и2000 соответственно. Очистка возраста ленивая, при завершении новых заданий. Active/delayed не очищаются этой политикой. Бизнес-история, подтверждения и unknown остаются в PostgreSQL. На отдельном Redis4010 завершённых/ошибочных вымышленных заданий сошлись к2000 completed и2000 failed; active/delayed сохранились. Измеренный used_memory около11.4MB относится только к этому тесту, не к10 мессенджерным аккаунтам.

## Шифрование и восстановление

Установлен age1.3.2 для Intel Mac в .tools/age из [официального выпуска](https://github.com/FiloSottile/age/releases/tag/v1.3.2). SHA256 архива проверен по опубликованному digest; provenance.json сохранён. Homebrew bottle для этой платформы отсутствует; компиляция Go и изменение доверия сторонним taps не выполнялись. [Документация age](https://github.com/FiloSottile/age#usage).

Ключ восстановления создан локально: .secrets/backup.agekey, получатель — .secrets/backup.recipient, права0600, каталог0700. Закрытый ключ не выводился и на VPS не передавался. .tools, .secrets и data/backups исключены из Git и Docker context. Ключ надо хранить отдельной офлайн-копией; Git его не восстанавливает.

`npm run backup:plan` показывает адрес и объём будущей операции без SSH. `npm run backup:init` создаёт новый ключ только при отсутствии старого; повторный вызов его не меняет. `npm run backup:database` — явное чтение реальной БД через SSH с StrictHostKeyChecking/BatchMode и шифрование потока на Mac. Незашифрованный dump на VPS или диске Mac не создаётся. Результат — data/backups/<время-UUID>/database.dump.age и manifest с размером/хешем. Успешный manifest пишется последним; сбой текущего запуска не изменяет прежние копии. Лимит файла по умолчанию2GiB и проверка свободного места; BACKUP_MAX_BYTES позволяет выбрать1MiB–10GiB. Старые копии автоматически не удаляются. Регулярная автоматизация не создавалась; Mac нужен включённым и доступным в момент копирования.

Текущий production CLI намеренно помечает комплект как **database-only / completeForDisasterRecovery=false**. Перед релизом комплект надо дополнить конфигурацией и APP_ENCRYPTION_KEY, согласованными снимками остановленных messenger profiles и ещё не истёкшими uploads. Это не заменено обещанием, что одного SQL достаточно. Живые профили Chromium не архивировать как заведомо согласованный снимок. Нужен конкретный порядок остановки владельцев/копирования/возврата перед утверждённым выпуском.

`work/backup-restore-smoke.mjs` проверяет реальный pg_dump→gzip→age→расшифровку→pg_restore в новой одноразовой БД на PG16.16. Локальный минимальный pg_dump собран без zlib, поэтому gzip выполняется отдельно; production Docker PostgreSQL использует собственное сжатие. Только после успешной аутентифицированной расшифровки начинается восстановление. Повреждение архива отклонено, перезапись копии запрещена, лимит размера проверен. Сохранились unknown с0 повторных отправок, manager hold, opt-out, курсор, source dedup и21 миграция. Временные БД/схемы/архивы/тестовые ключи удалены. Это доказательство механики восстановления, не резервная копия production.

## Контур live

`docker-compose.live.yml` — явный opt-in overlay для owned MAX, WhatsApp и AI coordinator. API сначала применяет базовую и AI-миграции; publishing worker делегирует MAX постоянному владельцу. MAX RPC не публикуется на host, проверяется внутренний health с секретом. SOURCE_MONITOR_ENABLED по умолчанию false, тестовая область по умолчанию включена; секрет владельца и GigaChat обязательны. Для коммерческого запуска нужен разрешённый коммерческий GigaChat; personal production вне тестовой области запрещается кодом владельца. Overlay только проверен Compose, на VPS не применялся.
