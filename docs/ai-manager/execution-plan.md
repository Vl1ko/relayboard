## 5. Архитектура и инварианты

Предпочтение: расширить существующий модульный backend и очереди, а не вводить микросервисную платформу, новый агентный фреймворк или векторную БД без доказанной необходимости. Один LLM provider adapter после выбора провайдера. Документацию SDK/API проверяй у выбранного поставщика на момент реализации; не угадывай endpoints и scopes.

Спроектируй совместимые модели: contacts и проверяемые channel identities; conversations по каналу/аккаунту; messages/inbound events; requests/leads с source identity; scenarios/templates/settings с версиями; follow-up plans; handoff events; durable outbound actions/receipts; opt-outs; review decisions. Новые каталоги/миграции создаются в ходе E02, их отсутствие сейчас не является ошибкой.

Обязательные инварианты для реализации и тестов:
1. Канонический контакт может иметь несколько подтверждённых channel identities. Истории/секреты аккаунтов не смешиваются. Не склеивай разных людей по отображаемому имени.
2. Уникальность события включает канал, аккаунт, диалог и внешний message/event ID. Уникальность логического первого обращения — контакт + согласованная заявка + тип действия, без параллельного повторения через другой канал.
3. PostgreSQL — источник бизнес-состояния и dedup; Redis — исполнитель. Одного jobId недостаточно: удалённая job теряет защиту по jobId.
4. Изменение бизнес-состояния и создание намерения внешнего действия — одна транзакция/outbox. Запись намерения не равна подтверждённой доставке. Не обещай exactly-once на неподконтрольном мессенджере.
5. Направление и происхождение сообщения различай отдельно: клиент; собственное подтверждённое сообщение сервиса; сообщение человека из исходного приложения; неопределённое. Одного fromMe недостаточно одновременно для запрета эха и native takeover.
6. Раздели qualification_status, automation_mode и delivery_status. Сбой доставки/LLM не означает «подходит», запись или заказ.
7. Перед каждым внешним действием заново проверяй opt-out, режим, актуальное поколение диалога, паузу, статус аккаунта, лимиты и рабочие часы. Устаревший ответ LLM или уже извлечённая job не должны обойти takeover/отказ.
8. Увеличивай automation generation/epoch при отмене; сериализуй конфликтующие действия диалога. Формулируй точную границу отмены: новое внешнее действие не начинается после зафиксированного запрета; уже начатый внешний вызов нельзя магически отозвать, его исход отображается отдельно.
9. Подтверждённые результаты и unknown не отправляются автоматически заново. Безопасные ретраи подготовки/чтения отличай от неоднозначного внешнего send.
10. Отказ/исключение переживает повторный импорт, поиск, рестарт и новое расписание. Снятие запрета не происходит побочно.
11. LLM возвращает валидируемую структуру: draft reply, извлечённые параметры/их источники, недостающие поля, предложение статуса, причина handoff. Сервер проверяет допустимые переходы и обязательные критерии. Модель не исполняет произвольные команды и не получает ключи/всю базу.
12. Версия знаний/критериев фиксируется для нового диалога. Изменение шаблона первого сообщения действует на ещё не начатые обращения; не заменяй эти два правила одним глобальным snapshot.
13. Браузер пользователя не исполняет фоновые AI/follow-up задачи. После его закрытия worker продолжает только разрешённое.
14. Бессрочные сырые payload, дубликаты медиа и тяжёлые логи не являются бесплатным способом отладки. Не удаляй dedup/unknown/активные источники по сроку обычного журнала.

## 7. Зависимости, параллельная работа и контроль сроков

Поиск можно интегрировать на fixtures, но финальная проверка зависит от реального существующего модуля.

Один владелец интеграции контролирует общие database/schema.sql, src/api/server.ts, src/worker/index.ts и web/src/App.tsx. Не допускай конкурирующих правок одних файлов и не передавай секреты/реальные данные новым исполнителям без требуемого разрешения.

Договорные контрольные точки, а не наша новая оценка:

## 9. Доказательства, состояние и Definition of Done

Создай один актуальный progress.md и матрицу:

    TZ-ID → этап → реализация/миграция → TC-ID → команда/ручной сценарий → ожидаемый результат → фактическое доказательство → статус.

Статусы этапов: NOT_STARTED / IN_PROGRESS / BLOCKED / READY_FOR_REVIEW / ACCEPTED.
Статусы проверок: PASS / FAIL / UNVERIFIED / NOT_APPLICABLE с обоснованием. Наличие файла, mock или старой записи тестов не означает PASS.

Для каждого этапа фиксируй:
1. Пользовательский/операционный результат.
2. Какие собственные файлы/миграции/конфигурации изменены.
3. Какие тесты запущены сейчас, какой результат и где артефакты.
4. Остаточные ограничения, внешние блокеры, следующий доступный этап.
5. Commit/version ID либо честное указание, что изменения ещё не закоммичены.

Исходные команды проверки существующего проекта:

    npm run typecheck
    npm test
    npm run build

Для retention integration tests используй только отдельную тестовую БД attachment_retention_test через RETENTION_TEST_DATABASE_URL; без переменной эти тесты пропускаются. Общая успешная команда с пропусками не подтверждает интеграцию.

Новые проверки должны быть воспроизводимы: изолированные PostgreSQL 16 и Redis, контролируемые часы для follow-ups, fixtures событий коннекторов, LLM fixtures плюс отдельно live API. Секреты передаются через штатный защищённый механизм окружения, не в текст доказательства.

Не вводи бессмысленный общий процент покрытия. Проверяй перечисленные бизнес-инварианты и границы ошибок. Тесты дублей/неверного адресата/отказа/takeover/unknown критичны; их FAIL блокирует выпуск.

Этап готов, когда измеримый результат подтверждён и применимые проверки пройдены. Бизнес-приёмку подтверждает человек; не отмечай ACCEPTED от его имени. Моки разрешают продвижение независимой разработки, но не снимают live release gate.

## 10. Выпуск и откат — отдельные последовательности

До production подготовь:
1. Чистый воспроизводимый release candidate и проверку, какие прежние незакоммиченные изменения включены/исключены.
2. Тест на копии схемы/данных PostgreSQL 16, утверждённые expand/backfill/contract шаги и окно совместимости старого/нового кода.
3. Согласованный backup БД, uploads, активных сессий и очереди там, где восстановление из БД не доказано; проверку восстановления на отдельном стенде.
4. Измерение доступного диска/RAM и пика обновления. Не собирать тяжёлые Docker-образы на заполненном VPS.
5. Режим остановки новых автоматических действий без потери уже начатого исхода; порядок API/worker/bridges/миграций, smoke и включения автоматики.
6. Стоп-условия: дубль, неправильный адресат, отказ не блокирует send, утечка/смешение аккаунтов, необъяснимый unknown, несовместимая миграция или нехватка рассчитанного ресурса.
7. План возврата в зависимости от фазы: до внешних действий — совместимый предыдущий код; после миграции — проверенная совместимость/restore; после отправленного сообщения — отмена дальнейших действий и разбор, а не «revert отменил отправку». Физически удалённые файлы требуют backup, смена retention-настройки их не восстанавливает.
8. Финальное разрешение на конкретный релиз, если оно ещё не дано; затем установка, live-проверки и пакет передачи.

Существующая авторизация на разработку не разрешает менять договор, покупать платные услуги, отправлять реальные рассылки вне тестового списка либо выполнять необратимое удаление данных без выбранной политики.
