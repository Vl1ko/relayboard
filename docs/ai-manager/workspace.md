# E10: рабочее место менеджера

Локальная реализация UI и авторизованного API поверх записанных данных, 13 ноября 2026. Не подтверждает полноту удалённой истории MAX/WhatsApp и не заменяет live E01/E13. Предыдущие демонстрационные контакты не используются этим компонентом.

## Интеграция

`createConversationRouter({pool,authorize,enabled,workflow:new ConversationWorkflow(pool)})` из `src/api/conversation-router.ts`; монтировать `/api/ai/workspace` перед общим `/api/ai` middleware импорта. Без `workflow` чтение базовых таблиц доступно, действия возвращают 503. `enabled=false` блокирует весь модуль после проверки авторизации. Все успешные/ошибочные ответы модуля имеют no-store; авторизация использует существующий единый административный контекст.

В тестовом режиме форма привязки выбирает контакт из первых100 импортированных, аккаунт и точный opaque ID диалога; вызывает root-owned `/api/ai/protocol/conversations`. Новая привязка не включает auto и не отправляет сообщение; тело запроса не выводится в лог.

Default UI `web/src/ConversationWorkspace.tsx`, стили `conversation-workspace.css`; включается владельцем App как отдельный раздел диалогов. Секреты и SQL-ошибки не выводятся. Доступные аккаунты берутся из существующего `/api/integrations`; отдельные канальные истории выбираются явно. Аккаунт и remote conversation ID видимы, включая удалённые legacy-аккаунты.

## API

- GET `/contacts`: поиск `q` по имени/телефону/записанному сообщению; буквальные `%`/`_` экранируются. Фильтры `status`, `mode`, `platform`, `accountId` должны совпасть в одном канальном диалоге. Сортировки recent/oldest/name; limit1–100, offset0–1e6. Одно подтверждённое contact ID показано одной карточкой, даже с двумя каналами; автоматического fuzzy-слияния нет.
- GET `/contacts/:id`: контакт и все привязанные диалоги; пагинация текстовой inbox-истории и последние100 outbox-операций. `conversationId` дополнительно ограничивает историю/операции выбранным диалогом и проверяется на принадлежность контакту. UI использует страницы50 сообщений, от новых к старым, внутри страницы — хронологический порядок. Намерения outbox показываются отдельно от записанной истории, без удвоения статуса доставки.
- GET `/conversations/:id/workflow`: последние20 уведомлений,50 followups и100 изменений статуса; без повторного чтения всей inbox-истории. Параметры и источник уведомления доступны в раскрываемом блоке карточки.
- POST `/conversations/:id/mode`: auto→explicit resume, manual→takeover, paused→stop. Все операции делегируются контактному workflow с отменой ожидающей автоматики, без небезопасного fallback на отдельное изменение SQL-режима.
- POST `/contacts/:id/opt-out`: сохраняет отказ контактно, его нельзя снять resume.
- POST `/conversations/:id/status`: все допустимые не-qualified статусы с обязательной причиной. Qualified нельзя назначить из браузера или протащить через proof: это требует серверной проверки критериев AI/workflow.
- GET `/settings`, PUT `/settings/manager`, PUT `/settings/followups`: явный адрес MAX-менеджера и правила всех4 сценариев. В форме выбираются timezone, рабочие дни/часы, последовательность задержек/текстов и лимит. Незаполненные данные не подставляются как бизнес-настройки.
- POST `/conversations/:id/followups`, `/cancel-followups`, `/handoff`: отдельное создание расписания с UUID idempotency key; отмена; запись передачи менеджеру с причинами human_requested/insufficient_data/reply_limit и резюме. Нет браузерного endpoint «подтвердить отправку уведомления». Уже записанные уведомления сохраняют снимок адреса назначения.

Интервал followup задаётся в секундах; начало отсчёта вводится в местном времени устройства, преобразуется в абсолютный ISO instant; рабочее окно считается серверным workflow в явно указанной timezone правила. Сохранение правила не отправляет сообщения. UI блокирует создание расписания по несохранённому изменению правила. Намерение отправки и уведомление со статусом pending не называются доставленными.

## Сводка и открытое решение O-10

Техническая схема `contact-presence-v1` — предложение до согласования бизнес-правил пяти счётчиков. Она всегда охватывает всю базу контактов с диалогами, независимо от текущих фильтров. Категории могут пересекаться, что явно написано в UI:

- новые: есть диалог new;
- подходящие: есть qualified;
- ожидающие: есть ai_dialog либо insufficient_data;
- закрытые: все привязанные диалоги closed/refused/unqualified;
- требующие проверки: есть manager_required/manager_working, unknown outbox либо записанное unresolved событие.

Историческое unresolved событие само не исчезает при takeover. До внедрения отдельного решения о снятии review-флага этот счётчик остаётся техническим, а не принятой бизнес-очередью. Этот модуль не объявляет O-10 закрытым.

## Ограничения и проверка

Ручная отправка из UI отключена с явным пояснением, пока нет доказанного транспорта с durable manual semantics. Доступно takeover и продолжение в исходном приложении с указанным аккаунтом; native outgoing detection зависит от реального адаптера. Собственные и человеческие сообщения различаются по записанному origin, неизвестный origin отмечается требующим проверки.

Outbox `synthetic_confirmation` либо external ID `synthetic:*` отображается как ТЕСТ: имитация, реальной отправки не было; обычное confirmed — подтверждение отправки каналом, не обещание чтения или конечной доставки клиенту. Уведомления с такими маркерами также не выдаются за реальные.

Новые файлы не меняют миграции/worker/существующий App. Тест `src/api/conversation-router.test.ts` требует отдельную `relayboard_workspace_test`, создаёт/удаляет свою случайную схему. Выполнено7 PostgreSQL18/HTTP тестов: авторизация/disabled, два канала в одной карточке/без секретов, буквальный wildcard и согласованные фильтры, пагинация/изоляция истории и принадлежность conversation ID, контактный takeover и сохранение unknown, opt-out против resume, серверный запрет browser-qualified, явные manager/followup settings без отправок и без browser ack. Typecheck PASS. Браузерные и PostgreSQL16/live проверки выполняет владелец общей интеграции; здесь они не объявляются пройденными.
