# E05/E07: проверяемое ИИ-ядро (offline)

Этот модуль не выбирает провайдера за пользователя. `AiSettings.provider` пока строго `unselected`, `model:null`; `AiProvider` принимает только `kind:'fixture'`. Реальный ИИ и договорная проверка на выбранной модели остаются O-02/O-05, а не считаются выполненными локальными тестами.

## Контракты

`AiEngineStore(pool, timeoutMs=15000)`:

- `settings()` → `{version, settings}`.
- `saveSettings({expectedVersion,settings})` создаёт неизменяемую новую версию под advisory lock; конфликт редакторов → `AiEngineError('settings_changed')`.
- `pinConversation(id)` возвращает строку pinned state. SQL-триггер фиксирует версию **при создании диалога**, а не при позднем вызове модели. Миграция фиксирует текущую версию для существующих диалогов.
- `evaluate(conversationId,eventKey,provider)` → сохранённая строка `ai_engine_decisions`: `id,conversation_id,event_key,settings_version,automation_epoch,disposition,business_status,reply,reason,fields`.
- `verifyAiQualification(client,conversationId,proofId)` — серверный verifier для workflow. Проверяет сохранённый qualified proof, его диалог/epoch/версию, auto и отсутствие opt-out. Браузерное утверждение «подходит» не является proof.

Настройки: `knowledge[{key,subject:general|price|availability|delivery_time,text}]`, `fields[{key,question,required}]`, `rules[{field,op:eq|gte|lte|one_of,value}]`, `qualificationEnabled`, `tone`, `replyLimit` и вышеуказанные provider/model. Настройки квалификации по умолчанию выключены; для включения необходимы явные обязательные поля и правила. Не введены выдуманные клиентские объёмы, регионы или цены.

## Граница доверия

Модель возвращает строго валидируемое предложение: извлечённые значения с message ID и точной цитатой, вид ответа, ключи известных фактов/вопросов, предложенный статус и причину handoff. `replyDraft` допускается в контракте, но **не отправляется и не сохраняется** как автоматический ответ. Сервер строит ответ только из настроенных текстов вопросов или knowledge. Неизвестный ключ, невалидная схема/enum, недостаточное доказательство или ошибка провайдера дают handoff без выдуманного ответа.

Извлечение принимается только из клиентских сообщений этого диалога, где действительно содержится цитата и соответствующее значение. Сервисные/человеческие/неопределённые исходящие не служат доказательством клиента. Подмена 12 на 12000, превращение -12/12.5 в 12 и пустое обязательное значение отклоняются. Это проверка локального происхождения, а не доказательство семантической безошибочности модели: сложные отрицания, единицы измерения и реальные коммерческие кейсы требуют согласованной спецификации и реальной проверки O-05.

Статус qualified выводится серверными правилами только при всех обязательных данных и выполненных критериях. Такой результат создаёт **handoff proposal**, а не самостоятельное изменение статуса/отправку. Нарушенное правило → предложение unqualified и обязательная проверка менеджером, без автоматического отказа клиенту; неполные данные не становятся qualified по предложению модели. Вопросы о цене/наличии/сроках без настроенных фактов, просьба человека и исчерпанный лимит дают handoff.

Вызов получает отдельные `system` и `data`; сообщения — данные, не команды. Контекст ограничен этим диалогом, последними20 событиями по4000 символов и его grounded state. В записи нет ключей провайдера, чужих контактов или сырых model payload. Settings/knowledge и история всё ещё могут содержать данные: для реального провайдера продолжают действовать O-03/O-04 и политика минимизации.

## Конкуренция и применение

Модель вызывается вне блокировок. Перед сохранением повторно проверяются contact opt-out, mode, статус и epoch, с порядком блокировок contact→conversation→state. Задержанный ответ после takeover/нового входящего отбрасывается. Дубликаты одного event сохраняют один decision и один расход лимита; уже сохранённый результат возвращается без нового вызова. Совпавшие concurrent provider calls могут начаться до сохранения первой записи: exactly-once сетевого вызова модели не заявляется.

`reply_count` — консервативный бюджет сохранённых намерений ответа, а не подтверждённых доставок. При лимите провайдер больше не вызывается. Внешний worker должен использовать устойчивый outbox key вида `ai-reply:<decision.id>`, заново проверить epoch/opt-out/mode непосредственно при enqueue/send и применить handoff через workflow. `evaluate` сам не создаёт outbox, не изменяет бизнес-статус и не отправляет сообщения. Возврат старого сохранённого decision после повторного события не отменяет необходимость этих guards.
