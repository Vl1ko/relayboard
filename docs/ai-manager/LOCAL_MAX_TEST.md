# Локальная проверка выбранного отправителя MAX

Актуальное поведение после уточнения пользователя: группа — только источник, ответ — в личку фактическому автору. Прежняя групповая проверка ниже — история и больше не доступна. Неотправленные групповые ответы отменены, неизвестные/подтверждённые исходы не удаляются.

Пользователь уточнил: ИИ пишет с подключённого аккаунта; при нескольких аккаунтах отправитель выбирается явно. Второй аккаунт нужен для проверки реального входящего диалога, но не для проверки исходящей отправки.

Локальный стенд: отдельная PostgreSQL БД relayboard_local_max, отдельный Redis, API только127.0.0.1, обычные sending workers выключены. Секреты — закрытый файл вне репозитория. LOCAL_MAX_TEST_CHAT_ID задаёт единственный разрешённый чат. Модуль дополнительно требует HOST=127.0.0.1 и точное имя выделенной локальной БД. В остальных окружениях форма скрыта, операции недоступны.

В «Подключениях» форма «Локальная проверка ИИ → MAX»: выбор подключённого MAX-аккаунта, вымышленная реплика клиента, подготовка ответа через настоящий GigaChat, предпросмотр и отдельная кнопка отправки в «Тестовая». Входящий текст имитируется явно; автоматического чтения переписки здесь нет. Настройки знаний и вопросов используются из существующего версионированного механизма. В пустой локальной БД первоначально заданы демонстрационные знания и вопрос про объём, а не реальные бизнес-условия.

Сервер проверяет accountId/actionId/chatId, доступность и принадлежность чата выбранному аккаунту, повторные guards ядра перед стартом. Для текста используется прямой синхронный Ws.send pinned UMax1.0.8 без await загрузки вложений/подключения внутри start. Сеть готовится до dispatch. Подтверждение только по actual server message ID; обрыв/неполный ответ — unknown без автоматического повтора. Уже обработанная операция не отправляется повторно. Форма сбрасывает предпросмотр при смене аккаунта или текста.

Проверено: 5 тестов local-router/MAX transport PASS; дополнительные 6 тестов GigaChat/MAX transport PASS; typecheck и production build PASS. Через настоящий GigaChat на синтетическом примере проверен строгий JSON-контракт: отсутствующие факты не извлекаются, askFields — массив строк. Браузерный предпросмотр выдал настроенный вопрос про объём от выбранного аккаунта. Кнопка отправки оставлена пользователю; live MAX receipt пока НЕ подтверждён.

Это локальная проверка исходящей отправки. Она не закрывает live receive/native takeover, постоянный MAX AI worker, WhatsApp, поиск и полную приёмку проекта.

Исправление после пользовательской проверки: при provider_failure ядро оставляет диалог на паузе; старый UI сообщал общую ошибку. Добавлены предварительная проверка режима до ingest/LLM, понятный статус и явная кнопка «Продолжить тест». Отказ/закрытый диалог продолжать нельзя. Устаревший cancelled preview отделён от unknown/confirmed. Ошибки соединения MAX до начала отправки показываются отдельно, busy освобождается даже при ошибке чтения credentials/подключения. 7 router/transport тестов PASS; typecheck/build PASS. Браузер подтвердил paused status и успешное явное продолжение. На момент диагностики все dispatch_started_at были NULL: отправок в MAX не было.


## Ответ в личку автору

Форма загружает последние20 сообщений только разрешённого тестового чата с выбранного аккаунта. Собственные, служебные и сообщения без подтверждённого sender исключаются. Пользователь выбирает исходную реплику; сервер хранит ограниченную по размеру и сроку ссылку на её accountId/messageId/authorId/text. Клиент не передаёт recipientId или текст источника при подготовке ответа. При смене аккаунта выбор и предпросмотр очищаются.

До подготовки и до отправки исходный message ID, автор и текст повторно сверяются с MAX. Личка определяется средствами pinned клиента, затем проверяется по независимому ответу MAX chat-info: DIALOG, ровно два участника — подключённый аккаунт и автор, адрес отличается от группы и Saved Messages. Текст модели не участвует в выборе адреса. Старые групповые action ID не имеют новой связи с источником и не могут отправиться через новый endpoint. Доступ к личке проверяется до финального dispatch. Источник и подтверждённая личка закрепляются в серверной связи с actionId; после рестарта/истечения TTL нужен новый предпросмотр. История ядра и unknown guards сохраняются.

Проверено:7 тестов router/author/transport PASS, typecheck/build PASS. В браузере новая форма и чтение тестового источника работают; подходящих сообщений другого участника пока нет. Пользователь подтвердил, что тестовый собеседник напишет в «Тестовая». Получение сообщения автора, разрешение его реальной лички и actual MAX receipt пока UNVERIFIED. Автоматический мониторинг/ответы остаются выключенными; отправка выполняется отдельной кнопкой.

## Автоматическая квалификация выбранной лички

После подтверждённого первого ответа появилась отдельная кнопка «Включить квалификацию по текущим настройкам». Это явный запуск одной локальной сессии выбранного accountId/authorId/private dialog. Текущее правило в вымышленном demo: volume>=10, модель GigaChat-2-Pro. Существующие пользовательские настройки вне распознанного demo не заменяются.

Сессия получает только последние сообщения закреплённой лички и передаёт новые реплики автора существующему AiOrchestrator. Периодический приём независим от ожидания модели: native ответ менеджера немедленно инвалидирует эпоху и отменяет поздний результат. Отправки имеют прежние guards и фактические подтверждения MAX. Собственные сообщения сопоставляются с подтверждёнными receipt ID; пока send ожидает acknowledgement, собственные сообщения откладываются до классификации. При отказе, takeover, unknown, потере соединения и завершении квалификации сессия останавливается. После рестарта автоматически не включается. Кнопка остановки ставит диалог на паузу; закрытие страницы само сессию не останавливает. Одновременно поддерживается одна локальная сессия, а не общий production worker.

Явный запуск новой фазы квалификации применяет актуальную версию настроек под contact/conversation locks, отменяет старые pending действия и follow-ups, увеличивает epoch. Если версия поменялась, рабочие поля пересобираются; исторические settings/decisions не переписываются. Opt-out/closed/refused/unknown не обходятся. При неизменной версии собранные параметры сохраняются.

GigaChat переведён на официальный response_format json_schema strict=true. Для числовых критериев JSON-схема требует число; сервер всё равно независимо проверяет цитаты, ключи и правила. Источник: https://developers.sber.ru/docs/ru/gigachat/guides/structured-output . Двухшаговая синтетическая проверка реального GigaChat-2-Pro PASS: запрос объёма → grounded12 → qualified. Первый прогон Lite без схемы выявил missing handoffReason/string number и был отклонён; огромная общая схема была заменена компактной после таймаута. TLS проверяется.

Проверено:5 новых PG16 integration тестов (квалификация, повтор, takeover при ожидающей модели, service echo, другой автор, отказ, unknown, смена настроек и opt-out);11 router/transport/provider тестов; typecheck/build PASS. Статусы и параметры отображаются в UI. Живая работа всех этапов через MAX и менеджерское уведомление пока требует пользовательской проверки. Уведомление handoff сохраняется штатным workflow; внешняя доставка менеджеру в этом локальном модуле не добавлена.

Исправление живого теста: первый private reply был подтверждён MAX, последующий параметр модель извлекла числом, отсутствующим в цитате; сервер отклонил его как ungrounded_extraction. После native сообщения менеджера диалог стал manual. По отдельному явному разрешению пользователя выполнен повтор только выбранного тестового диалога через GigaChat без вывода его текста и без новых отправок MAX. После ограничения evidence IDs/quotes исходными сообщениями и числовых значений буквальными кандидатами клиента проверка стала qualified. Правила доказательности сервера не ослаблялись.

При явном новом запуске сессия пропускает уже сохранённые inbox IDs и собственные сообщения, существовавшие до нажатия запуска: старое вмешательство менеджера не срабатывает повторно. Новое сообщение менеджера по-прежнему останавливает ИИ. Повторный предпросмотр ручного диалога может вернуть уже подтверждённый первый ответ и кнопку явного запуска, без повторной отправки. История и unknown guards сохраняются. Добавлен integration test этого сценария. Итог:6 session DB tests,5 provider tests и3 router tests PASS, typecheck/build PASS. После обновления автоматика не включается без явного запуска.

## Финальное подтверждение клиенту

Живой тест дошёл до qualified: отсутствие ответа оказалось отсутствующим продуктовым шагом после успешной квалификации, а не сбоем приёма. Добавлена явная миграция11 — qualification_notice в общем durable outbox. Сообщение фиксировано сервером: «Спасибо, параметры заявки сохранены.»; не обещает цену, сроки или факт доставки уведомления менеджеру.

Подтверждение привязано к принятому qualified/unqualified решению и завершённому handoff, текущей эпохе, тому же контакту/личке и paused результату. Это не возобновление общего auto-режима. Общий dispatch повторно проверяет account/auth, opt-out, takeover, epoch, точный текст и proof chain; unknown/dispatching другого действия блокирует старт. Уникальный logical key на decision предотвращает повтор. При takeover до начала notice отменяется. Сессия отправляет notice перед завершением; отдельная кнопка восстановления позволяет отправить пропущенный итог уже завершённой проверки.

Миграция11 применена только локально. Последовательный прогон33 DB тестов PASS (первый параллельный прогон конфликтовал при CREATE EXTENSION pgcrypto в общей тестовой БД); typecheck/build PASS. В браузере восстановлен пропущенный итог разрешённому тестовому автору: UI получил confirmed от MAX, кнопка восстановления скрылась. Доставку/прочтение клиентом не утверждаем: подтверждена серверная отправка.
