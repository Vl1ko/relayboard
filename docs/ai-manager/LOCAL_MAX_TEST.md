# Локальная проверка выбранного отправителя MAX

Актуальное поведение после уточнения пользователя: группа — только источник, ответ — в личку фактическому автору. Прежняя групповая проверка ниже — история и больше не доступна. Неотправленные групповые ответы отменены, неизвестные/подтверждённые исходы не удаляются.

Пользователь уточнил: ИИ пишет с подключённого аккаунта; при нескольких аккаунтах отправитель выбирается явно. Второй аккаунт нужен для проверки реального входящего диалога, но не для проверки исходящей отправки.

Локальный стенд: отдельная PostgreSQL БД relayboard_local_max, отдельный Redis, API только127.0.0.1, обычные sending workers выключены. Секреты — закрытый файл вне репозитория. LOCAL_MAX_TEST_CHAT_ID задаёт единственный разрешённый чат. Модуль дополнительно требует HOST=127.0.0.1 и точное имя выделенной локальной БД. В остальных окружениях форма скрыта, операции недоступны.

В «Подключениях» форма «Локальная проверка ИИ → MAX»: выбор подключённого MAX-аккаунта, вымышленная реплика клиента, подготовка ответа через настоящий GigaChat, предпросмотр и отдельная кнопка отправки в «Тестовая». Входящий текст имитируется явно; автоматического чтения переписки здесь нет. Настройки знаний и вопросов используются из существующего версионированного механизма. В пустой локальной БД первоначально заданы демонстрационные знания и вопрос про объём, а не реальные бизнес-условия.

Сервер проверяет accountId/actionId/chatId, доступность и принадлежность чата выбранному аккаунту, повторные guards ядра перед стартом. Для текста используется прямой синхронный Ws.send pinned UMax1.0.8 без await загрузки вложений/подключения внутри start. Сеть готовится до dispatch. Подтверждение только по actual server message ID; обрыв/неполный ответ — unknown без автоматического повтора. Уже обработанная операция не отправляется повторно. Форма сбрасывает предпросмотр при смене аккаунта или текста.

Проверено: 5 тестов local-router/MAX transport PASS; дополнительные 6 тестов GigaChat/MAX transport PASS; typecheck и production build PASS. Через настоящий GigaChat на синтетическом примере проверен строгий JSON-контракт: отсутствующие факты не извлекаются, askFields — массив строк. Браузерный предпросмотр выдал настроенный вопрос про объём от выбранного аккаунта. Кнопка отправки оставлена пользователю; live MAX receipt пока НЕ подтверждён.

Это локальная проверка исходящей отправки. Она не закрывает live receive/native takeover, постоянный MAX AI worker, WhatsApp, поиск и полную приёмку проекта.

Исправление после пользовательской проверки: при provider_failure ядро оставляет диалог на паузе; старый UI сообщал общую ошибку. Добавлены предварительная проверка режима до ingest/LLM, понятный статус и явная кнопка «Продолжить тест». Отказ/закрытый диалог продолжать нельзя. Устаревший cancelled preview отделён от unknown/confirmed. Ошибки соединения MAX до начала отправки показываются отдельно, busy освобождается даже при ошибке чтения credentials/подключения. 7 router/transport тестов PASS; typecheck/build PASS. Браузер подтвердил paused status и успешное явное продолжение. На момент диагностики все dispatch_started_at были NULL: отправок в MAX не было.


## Ответ в личку автору

Форма загружает последние20 сообщений только разрешённого тестового чата с выбранного аккаунта. Собственные, служебные и сообщения без подтверждённого sender исключаются. Пользователь выбирает исходную реплику; сервер хранит ограниченную по размеру и сроку ссылку на её accountId/messageId/authorId/text. Клиент не передаёт recipientId или текст источника при подготовке ответа. При смене аккаунта выбор и предпросмотр очищаются.

До подготовки и до отправки исходный message ID, автор и текст повторно сверяются с MAX. Личка определяется средствами pinned клиента, затем проверяется по независимому ответу MAX chat-info: DIALOG, ровно два участника — подключённый аккаунт и автор, адрес отличается от группы и Saved Messages. Текст модели не участвует в выборе адреса. Старые групповые action ID не имеют новой связи с источником и не могут отправиться через новый endpoint. Доступ к личке проверяется до финального dispatch. Источник и подтверждённая личка закрепляются в серверной связи с actionId; после рестарта/истечения TTL нужен новый предпросмотр. История ядра и unknown guards сохраняются.

Проверено:7 тестов router/author/transport PASS, typecheck/build PASS. В браузере новая форма и чтение тестового источника работают; подходящих сообщений другого участника пока нет. Пользователь подтвердил, что тестовый собеседник напишет в «Тестовая». Получение сообщения автора, разрешение его реальной лички и actual MAX receipt пока UNVERIFIED. Автоматический мониторинг/ответы остаются выключенными; отправка выполняется отдельной кнопкой.
