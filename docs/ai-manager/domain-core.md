# E02 — транзакционное ядро, offline-инкремент

Дата: 12 ноября 2026. Статус: READY_FOR_REVIEW только для описанного ядра. Полный E02 и договорная приёмка не завершены.

## Реализация

- database/ai-manager.sql — отдельная additive-миграция v1.
- src/core/ai-manager-migration.ts — транзакционное применение с advisory lock, проверкой базовой схемы, историей и SHA256. Повтор не переписывает данные; изменение применённой миграции отклоняется.
- src/api/migrate-ai-manager.ts — явная CLI-команда, не добавленная в текущий production startup.
- src/core/ai-manager.ts — внутренний store, не публичный HTTP API и не обработчик живого аккаунта.
- src/core/ai-manager.test.ts — синтетические интеграционные проверки на настоящей отдельной PostgreSQL.

В этом инкременте нет фоновых задач, импорта, LLM-запросов, live adapter или новых UI/API маршрутов. Модуль при импорте не подключается к сети/БД и не читает runtime config.

## Состояние и транзакции

ai_contacts хранит явно созданный канонический контакт и устойчивый opt-out. Автоматическое слияние по имени/номеру не реализовано. Привязку контакта к аккаунтному external dialog ID обязан явно установить вызывающий код по проверенной идентичности.

ai_conversations хранит отдельные business_status, automation_mode и automation_epoch. БД знает девять допустимых статусов, но переходы «подходит»/«не подходит» и правила критериев ещё не реализованы: O-05 открыт. Новые диалоги paused; auto включается явной командой. Повтор той же команды режима не сбрасывает новые задания.

ai_inbox сохраняет одно нормализованное сообщение по channel event key. INSERT и изменение режима/поколения/отмена ожидающих действий — одна транзакция. Duplicate replay возвращает исходную запись и не повторяет эффект; другое тело с тем же message ID не переписывает историю и не становится новым событием редактирования.

Service echo не вызывает takeover. Подтверждённый native human переводит в manual; unresolved — в paused, а не в «клиент». Клиентский ответ увеличивает epoch и отменяет старые pending actions: это консервативное правило, не механизм квалификации. Inbox пока не запускает обработчик/LLM-job автоматически.

ai_outbox — устойчивое намерение, не факт доставки. Дедупликация по contact/kind/logical_key работает между явно связанными каналами; ключ заявки предоставляет вызывающий код. Семантика «та же заявка» остаётся O-06, никакое произвольное окно в днях не выбрано. Повтор с другим текстом требует явной операции изменения, а не молчаливой подмены idempotency key. Редактирование ещё не начатых шаблонов предстоит в E04.

Неизменяемый внешний operationId — UUID записи outbox. Состояния pending/dispatching/confirmed/rejected/unknown/cancelled разделены. Rejected и unknown сейчас не переотправляются автоматически. Для безопасного нового рассмотрения rejected нужны отдельная политика/команда; unknown требует сверки либо человека. Именованное прерванное выполнение сохраняет uncertainty и никогда не сбрасывается в pending.

## Отмена и граница внешнего вызова

Порядок блокировок: contact → conversation → action; account FOR SHARE на финальном guard. Opt-out охватывает все явно связанные диалоги. Pending отменяется; начавшаяся попытка получает cancellation_requested, а позднее подтверждение сохраняется как факт. Ожидание внешнего ответа не держит контакт заблокированным.

Транспорт предварительно готовится вне транзакции: соединение, поиск peer, медиа и формирование payload. PreparedChannelSend.start обязан **синхронно начать уже подготовленный запрос** и вернуть envelope с Promise подтверждения. Нельзя передавать старый async MAX.send с внутренними await getClient/chats.get. Явный AsyncFunction отклоняется до вызова, но эта проверка не доказывает отсутствие скрытого await/очереди в обычной функции.

Сначала сохраняется dispatching, затем под повторной блокировкой проверяются opt-out/mode/epoch/account и вызывается start. Обновление отказа после durable claim, но до start, проверяется повторно. Между start и результатом отказ останавливает будущие действия, но не «отменяет» уже начавшийся внешний эффект. Если процесс/COMMIT теряется, dispatching остаётся для консервативной сверки.

Подготовленный транспорт явно связан с accountId/platform/externalConversationId. Перед claim сверяется точное совпадение с сохранённым диалогом; транспорт другого аккаунта/получателя отклоняется без внешнего вызова.

Конкретных подготовленных адаптеров пока нет. Для каждого нужен отдельный release-gate тест фактической границы send и отсутствия скрытых повторов; текущие fixtures не доказывают свойства MAX/WhatsApp.

## Совместимость и миграция

Перед применением требуются базовые integrations(id,platform,enabled,auth_error). Запуск на неполной схеме завершается ошибкой с откатом. Старые posts/deliveries/retention и их runner не изменены.

account_id/platform сохраняются как snapshot, без FK на integrations: прежний hard DELETE аккаунта не получает новый 23503 и не удаляет историю. Создание диалога проверяет существующий MAX/WhatsApp account под FOR SHARE. Отсутствующий аккаунт отменяет pending действие; disabled/auth_error оставляет его ожидающим. Доступ к историческим account IDs не заменяет авторизацию будущего публичного API.

Применять пока только на отдельном тестовом стенде:

    node dist-node/api/migrate-ai-manager.js

CLI использует явную конфигурацию БД из окружения. Не применять на production до проверки PostgreSQL16 и состава baseline. После выпуска v1 неизменна; дальнейшие изменения только новыми версиями миграций. Откат кода оставляет новые таблицы/историю; удаление таблиц не является безопасным rollback.

## Проверки и ограничения

Тестовая переменная AI_MANAGER_TEST_DATABASE_URL принимает только БД relayboard_ai_manager_test; каждый запуск использует свою временную схему. Production и реальные сессии не используются.

    AI_MANAGER_TEST_DATABASE_URL=postgresql://localhost/relayboard_ai_manager_test \
      node --import tsx --test src/core/ai-manager.test.ts

Подтверждаются конкурентные дубли, account scope, atomic rollback, stale generation, persistent opt-out двух каналов, echo/manual/unresolved, cross-channel operation key, одна попытка отправки, auth loss/restore, неверный/потерянный ack, прерванный worker и поздний результат, подготовка после отказа, отмена между claim/start, совместимость удаления аккаунта, проверка checksum/отката миграции.

Среда этого запуска — PostgreSQL18.3, не целевая PostgreSQL16. Итоги полного набора и сборки — progress.md. Выбор провайдера, критерии, request identity, реальные коннекторы, миграция PG16, рабочие часы/лимиты, публичный API/права, inbox processing orchestration и UI остаются последующими задачами. По текущим fixtures нельзя заявлять полное выполнение E02–E07 или exactly-once внешней платформы.
