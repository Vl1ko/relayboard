# Постоянное исполнение — состояние разработки

Компоненты проверены изолированно; это не подтверждение полного релиза. Поиск новых источников, phone routing, WhatsApp AI и общая приёмка ещё завершаются по RELEASE_PLAN.md.

## Владение

- `start:max-worker`: один владелец MAX WebSocket; API discovery, AI, менеджерские уведомления и прежние публикации обращаются к нему.
- `start:ai-worker`: один исполнитель решений и очередей; фактическую отправку выполняет владелец транспорта.
- `start:worker`: один исполнитель прежних публикаций. Второй процесс ждёт ownership и не исправляет работающие отправки первого.
- PostgreSQL advisory ownership имеет heartbeat. При потере владения работа отменяется, начатые отправки остаются unknown. Новый владелец не повторяет их. Входящий inbox, outbox, решения, фазы и курсоры хранятся в БД.

MAX RPC закрыт отдельным секретом, без публичного порта. При настройке `MAX_WORKER_URL` API читает группы через общий сокет, публикации передают только durable delivery ID. Старый локальный transport выключается. Первую установку нужно выполнять после остановки старых процессов, не использующих ownership.

## Конфигурация тестового стенда

Закрытый env-файл, права 0600; ключи и токены не печатать и не помещать в Git:

```dotenv
AI_SEND_MODE=live
AI_PROVIDER_MODE=gigachat
AI_ALLOW_EXTERNAL_REQUESTS=true
AI_TEST_ONLY=true
AI_TEST_ACCOUNT_IDS=<UUID разрешённого тестового аккаунта>
AI_TEST_AUTHOR_IDS=<ID разрешённого тестового собеседника>
MAX_WORKER_ENABLED=true
MAX_WORKER_HOST=127.0.0.1
MAX_WORKER_PORT=3030
MAX_WORKER_URL=http://127.0.0.1:3030
MAX_WORKER_SECRET=<отдельный случайный секрет минимум 24 символа>
MAX_POLL_INTERVAL_MS=5000
```

GigaChat credential, scope, CA, DATABASE_URL и остальные обязательные настройки задаются в том же закрытом окружении. Для коммерческого production без тестового ограничения worker отклоняет PERS. Смена флага не оформляет поручение на обработку данных и не покупает коммерческий доступ.

Перед запуском применяются base schema и `db:migrate:ai` (версия 14), собирается приложение. MAX и AI worker запускаются отдельными постоянными процессами с тем же закрытым окружением. В production нужен утверждённый release runbook и supervisor; локальный `npm run` не заменяет deployment.

В режиме `synthetic` выполняются только fixture-подтверждения. Сочетать его с live MAX owner нельзя. Live AI отклоняет fixture-провайдер, отсутствие ключа/внешнего разрешения/списка тестовых аккаунтов и собеседников.

## Входящие сообщения

Личная переписка читается только для привязанной активной фазы и проверенного автора. Пагинация догружает пропуск до сохранённого курсора, включая границу timestamp; неполная догрузка не продвигает курсор. Новый экземпляр продолжает с БД, а не с содержимого браузера. Повтор события не меняет epoch повторно.

Перед отправкой актор ждёт синхронизации лички. Подтверждённый ID программы считается service echo; неподтверждённый собственный результат ждёт receipt или вызывает unresolved hold. Собственное сообщение из приложения менеджера включает ручной режим. Старый batch не может записаться в новую фазу.

Смена критериев по явному запуску архивирует предыдущую фазу, сохраняя её версию, поля и счётчик. Старая pending notification не отправляется в следующей фазе. Обычное дополнительное сообщение клиента после квалификации сохраняет manager hold и не отменяет единственное настроенное сообщение ожидания; opt-out и ручной takeover по-прежнему отменяют его.
