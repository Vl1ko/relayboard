# Полное восстановление Relayboard

Инструмент `scripts/recovery-bundle.mjs` упаковывает **уже согласованные снимки**. Он не останавливает сервер и не объявляет копию живого Chromium согласованной. Настоящее production-копирование выполняется в финальном окне F08; сейчас проверены только вымышленные данные.

## Состав

Спецификация содержит `version:1`, `quiesced:true`, `releaseCommit`, `capturedAt` и абсолютные пути `databaseFile`, `configFile`, `queueFile`, `uploadsDir`, `profilesDir`. Каждый обязательный путь должен существовать. `configFile` имеет права0600 и включает APP_ENCRYPTION_KEY. Ключ age находится отдельно в `.secrets/backup.agekey`, получатель — `.secrets/backup.recipient`; не включать закрытый ключ age в собственный архив.

Пакет включает PG custom dump, конфигурацию, Redis snapshot, uploads и каталоги профилей. Manifest с именами/размерами/SHA256 шифруется вместе с содержимым. Файлы читаются потоком, меняющийся источник и symlink отклоняются. Общий лимит по умолчанию4GiB. Существующий архив не перезаписывается.

```sh
npm run backup:bundle -- pack /private/tmp/relayboard-snapshot/spec.json /private/tmp/relayboard-recovery.age
npm run backup:bundle -- restore /private/tmp/relayboard-recovery.age /private/tmp/relayboard-recovered-new
```

`restore` допускает только новый каталог с правами0700. Файлы имеют0600; выход за каталог, повторы имён, усечение, превышение лимита и неверный hash отклоняются. Расшифровка age должна успешно подтвердиться **до** создания COMMITTED.json. При ошибке незавершённый новый каталог удаляется; прежний каталог не меняется. Инструмент не запускает восстановленные сервисы и не отправляет сообщения.

## Порядок для production

1. Зафиксировать release/image/Compose, текущие режимы, очередь и начатые/unknown исходы. Проверить место на источнике и Mac. Дождаться подтверждений либо сохранить неопределённость; не превращать её в разрешение повтора.
2. В согласованное окно остановить писателей: API, publishing/AI workers и владельцев MAX/WhatsApp/Telegram. Не уничтожать volumes. При остановке Chromium дождаться завершения процесса. PostgreSQL/Redis оставить для создания снимков.
3. Получить согласованный PG dump и Redis RDB, копию необходимой конфигурации и того же APP_ENCRYPTION_KEY, ещё не истёкших uploads и закрытых профилей. Зафиксировать фактическое время и версию. При symlink/изменяющемся профиле выяснить причину, не обходить проверку.
4. Передать по SSH с проверкой host key, упаковать/проверить age и скопировать итог на Mac. Пароли, .env и профили не выводить в чат, Git и build context. Удалять только созданные текущей операцией временные plaintext-копии после подтверждения архива. Возобновить только те сервисы/режимы, которые работали до окна.
5. Для восстановления поднять отдельные пустые PG16/Redis, вернуть dump/RDB и файлы с правильными владельцами/путями. Применить идемпотентные миграции, не изменяя прежние checksum. Сначала API с выключенными внешними действиями; проверить карточки, настройки и protective states.
6. Проверить сохранность dedup/cursors/holds/opt-out/unknown. Redis-job сам по себе не доказывает, что отправка не началась: бизнес-исход из БД имеет приоритет. При возврате на снимок учесть внешние сообщения, отправленные **после** снимка; без сверки они могут повториться. До завершения сверки senders не включать.
7. Только после реальной проверки авторизации и разрешения рабочего контура запускать владельцев, затем workers и мониторинг в нужной области. Восстановление настоящих профилей требует F08; синтетический файл сессии не подтверждает реальный вход MAX/WhatsApp.

## Ротация

`npm run backup:retention` только показывает план: по умолчанию сохранить7 копий и возраст30 дней. Применение — отдельный явный `npm run backup:retention -- --execute`; параметры задаются BACKUP_KEEP_COUNT/BACKUP_MAX_AGE_DAYS. До выбора владельцем политики реальное удаление не выполняется. Инструмент распознаёт только завершённые database-only каталоги своего CLI, сверяет hash и сохраняет как минимум самую свежую распознанную копию; неизвестные/повреждённые/неполные каталоги не трогает. Полные `.age` bundles этим удалением не охватываются и сохраняются отдельно до выбора политики.

Копия на выключенном/недоступном Mac не создаётся автоматически. Расписание/RPO, ротацию полных bundles и отдельную офлайн-копию ключа владелец подтверждает в F08. Срок хранения рабочих текстов и срок хранения резервных копий — разные политики.
