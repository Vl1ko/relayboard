# E09: источники заявок и проверка кандидатов

Подключённого поиска в исходном проекте нет (O-01). Этот инкремент реализует durable intake/review и контракт будущего источника; не изображает существующий поиск, мониторинг реальных групп, автоматическую классификацию или live обращение. UI явно отмечает ручные/тестовые данные. Реальные данные и интеграция поиска требуют O-01/O-03/O-04.

## Данные и дедупликация

`LeadIntakeStore.ingest(source)` принимает platform `max|whatsapp|telegram`, accountId UUID, непрозрачные chatId/authorId/messageId, occurredAt с timezone, original text, необязательную http(s)-ссылку, sourceKind `manual|fixture`, params и confidence0..1. Стабильный source key — platform/account/chat/message; идентификаторы не обрезаются. Автор, timestamp, ссылка и исходный текст защищены fingerprint: конфликтующее содержимое того же события отклоняется, исходная запись не перезаписывается.

Оценка уверенности здесь — заявленное ручным/тестовым источником число, а не доказательство калиброванной модели. Даже confidence=1 создаёт только pending candidate. Параметр `{key,value,evidenceQuote}` должен подтверждаться точной цитатой оригинального текста и значением в ней. Нет придумывания цены по тексту «бюджет не назван» или изменения знака числа через обрезанную цитату. Проверка цитаты не доказывает бизнес-семантику отрицаний/единиц измерения; все кандидаты требуют человека.

Повторная доставка сообщения возвращает ту же запись, включая уже approved/rejected результат. Простое повторение источника не оживляет отклонённую заявку, не создаёт контакт, диалог, business request или outbox. Разные события не объединяются по имени/аватару/похожести текста.

## Явная проверка

`review({leadId,operationId,expectedRevision,action,params?,contactId?,requestId?,reason?})`:

- edit меняет только параметры pending-кандидата с проверкой цитат и revision; оригинальный текст остаётся прежним.
- approve требует явные contactId + requestId. В одной транзакции существующая заявка проверяется на принадлежность контакту либо создаётся новая ai_requests запись; opt-out блокирует approval. Два сообщения можно осознанно привязать к одной существующей заявке, чтобы не создавать второе первое обращение.
- reject требует причину; approved/rejected не редактируются побочным повтором источника.

`operationId` сохраняет атомарную квитанцию. Повтор той же операции возвращает прежний результат; повтор ID с другим содержимым отклоняется. Изменение другого редактора требует обновления списка. Ошибка записи квитанции откатывает одновременно approval и созданную заявку. Сам approve **ничего не отправляет**, не меняет режим диалога и не подтверждает доступность автора в личных сообщениях. Дальнейший запуск через общий workflow обязан применять request-level dedup/guards и правила unknown.

## HTTP и интерфейс

Factory `createLeadRouter({pool,authorize,enabled})`, root mount `/api/ai/leads`:

- GET `/` → `{leads,total}`; status pending/approved/rejected, limit1–100, offset; без status возвращаются все.
- POST `/` → `{lead,replayed}` для ручного/синтетического intake.
- POST `/:id/review` → `{lead,replayed}`; путь задаёт leadId, body не может подменить его.

Все endpoint требуют администратора и включённого feature flag, возвращают no-store. SQL/payload details не логируются. Ссылка источника не загружается сервером; UI разрешает открыть только http(s) в отдельной вкладке с noopener/noreferrer. Тексты/цитаты показываются как React text, не HTML/команды.

`LeadReview` показывает pending/approved/rejected, оригинал, автора/беседу/аккаунт, дату, ссылку, confidence, параметры и причину. Параметры пока редактируются структурированным JSON с точными цитатами; production-friendly редактор полей можно улучшить отдельно. Привязка — к явно выбранному контакту и существующей либо новой заявке. Контакты и доступные существующие заявки ограничены первыми/последними100, список источников — страницами25. При потере ответа UI повторяет тот же operationId, а не генерирует второе approval.

## Миграция и ограничения

Миграция additive `ai-manager-leads.sql` после ai_requests: исходные записи, review revision и durable receipts. Старая сборка игнорирует новые таблицы; rollback приложения не должен удалять источники, ключи dedup и approval receipts. Срок их удаления остаётся O-09; случайный TTL как у debug-логов не применяется.

Сохранение экономит место: один оригинал на message identity, без загрузки медиа/экспорта чатов/сырого ответа модели. Текст ограничен8000 символами, параметры30 с quote≤1000/value≤500, ссылка≤2048. Полная долговременная политика и реальная нагрузка ещё требуют согласования/замера.

`LeadSourceAdapter` — будущий read(cursor) контракт внешнего поиска, не подключённая реализация. Новому реальному адаптеру нужны capability evidence, правильный account namespace и разрешения; ручной intake не заменяет TZ-2.8 live-приёмку.

Проверки:12 unit/PG/HTTP случаев — schema/url/confidence, 5 конкурентных ingest, immutable-content conflict, namespace/opaque IDs, grounded params, concurrent approve/replay, 2 источника→1 request, opt-out/rebind conflict, revision edit, persistent reject/reingest, rollback receipt, auth/flag/validation/routes. БД только relayboard_lead_test; фактические результаты root фиксирует в progress.md. Локально PG18, PG16/live search не проверялись.
