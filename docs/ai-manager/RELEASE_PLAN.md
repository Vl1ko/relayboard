## 3. Изменения архитектуры и данных

- Сохранить Node24/TypeScript/Express/React, PG16, Redis/BullMQ. Новый стек и отдельный продукт не нужны.
- Существующие `AiManagerStore`, `AiEngineStore`, `AiOrchestrator`, `ConversationWorkflow`, `OutreachRunner` остаются ядром. Транспорт нормализует доверенное происхождение события до ingest; текст клиента и ответ модели не выбирают аккаунт/получателя.
- В БД явно связать `ai_requests`, источники, фазы диалогов и outbox. Добавить устойчивые source cursors, leases/checkpoints, версионированные search/routing/follow-up настройки, priority и retention metadata. Точная схема проектируется в RES01 до миграции, а не объявляется уже существующей.
- У каждого автоматического внешнего действия устойчивый operation/logical key; confirmed и unknown не получают слепого повтора. Корреляция service echo и native human должна работать во всех workers/bridges, а не только в памяти одного процесса.
- Общая очередь запросов модели считает квоту по credential.20 активных диалогов могут ждать клиента, но на Freemium/PERS нельзя предполагать20 параллельных model requests. Коммерческий scope/лимит подтвердить до установки значений concurrency.
- Один процесс/владелец сессии на аккаунт; чтение списка групп, API и публикационный worker не должны конкурировать за MAX WebSocket. WhatsApp sessions должны быть изолированы.
- Настройки зафиксированы по фазе/заявке. Изменение правил не переписывает принятые решения старой заявки; новый закрытый→новый source процесс не тянет старые поля/лимиты/manager hold.

Изменяемые существующие области: `src/core/ai-manager*.ts`, `ai-engine.ts`, `ai-orchestrator.ts`, `begin-qualification.ts`, `conversation-workflow.ts`, `lead-intake.ts`, `search-sources.ts`, `outreach*.ts`, `src/ai-worker/index.ts`, adapters/bridges, API routers, UI panels, docker-compose*.yml, `database/` и документация. Новые cursor/lease/request-phase модули и миграции создаются соответствующими RES; неизвестные имена файлов не выдаются за уже существующие.

## 6. Хранение

-30 дней считаются после фактического завершения заявки: manager-held/active не удаляются как завершённые. Неудачную отправку неизвестного результата очистка не превращает в успешную.
- Удалить полные тексты и дубли из inbox, source originals, evidence quotes/JSON, summary, очередей/логов по согласованной политике. Нужный минимум для дедупа/исключений/аудита исхода хранится отдельно без полного текста; саму базу контактов эта политика автоматически не удаляет.
- Вложения публикаций: сохранить уже согласованную политику30 дней, не удалять активные/регулярные/приостановленные.
- Внешние сообщения в MAX/WhatsApp не удаляются очисткой локальной БД. Резервные копии имеют свою согласованную ротацию: нельзя обещать исчезновение текста из backup без её настройки.
- Очистка небольшими транзакциями/пакетами, повтор безопасен, есть preview/метрики. На заполненном диске не запускать VACUUM FULL без рассчитанного места; размер/индексы/WAL измерять до изменения.

## 7. Ресурсы и безопасность

Текущий VPS:2GB RAM, available около258MiB, swap полностью занят; диск15GB/76%. Один WhatsApp контейнер занимает около702MiB. Это не испытание5 WhatsApp sessions; обещать10 аккаунтов на этом VPS нельзя. На RES09 определить размер RAM/диска и размещение browser bridges по измеренному пику. Конкретную покупку/апгрейд согласовать после расчёта.

Свежий audit содержит17 замечаний (11high/6moderate). Исправить достижимые уязвимости совместимыми обновлениями; недостижимые/оставшиеся обосновать с конкретными ограничениями и планом, не делать слепой npm audit fix --force. Проверить auth/CSRF/origin, доступ к attachments и разделение аккаунтов, секреты в logs, сохранность сессий, зависимости и инструкции восстановления. Это задачи проверки фактических рисков, не новая функциональность продукта.

## 8. Выпуск и возврат

1. Утверждённый код/образ/manifest; все изменения исходного dirty baseline учтены. Точные lockfile и миграции.
2. Резервная копия production БД, uploads, активных сессий и критичных очередей; off-host копия и тест восстановления. Не печатать env/сессии и не копировать их в git.
3. Проверить миграции/backfill на отдельной PG16 копии. Только additive расширения с описанной совместимостью старого и нового кода; не переписывать уже применённые checksums.
4. Собрать image вне тесного VPS. Установить отдельный RC с отключёнными внешними действиями; smoke, ресурсы, auth, old-feature regression.
5. Приостановить создание новых автоматических действий, дождаться/зафиксировать начатые исходы; сохранить current image/compose и release-specific secrets/config.
6. Применить проверенные миграции, запустить API/bridges/worker по порядку; проверить очереди/health и только затем включать разрешённые сценарии.
7. Перед production — отдельное подтверждение конкретного готового выпуска. Ни утверждение плана, ни тесты не означают разрешение на новую массовую рассылку/платёж.
8. После установки — live smoke обоих каналов, сверка12/12, мониторинг очередей/ошибок, инструкции пользователю.

Стоп выпуска: неверный адресат, дубль, нарушение opt-out/manager hold, утечка/смешение аккаунтов, неизвестный исход без блокировки, несовместимая миграция или недостаток ресурсов. Возврат: отключить новые действия, сохранить started/unknown, вернуть совместимый предыдущий образ. Новые таблицы/историю не удалять ради revert. Восстановление backup — только по проверенному сценарию с учётом уже отправленных сообщений; отправленное сообщение откат кода не отменяет.

## 9. Что нужно утвердить

- Порядок RES00–10 и полный объём обоих мессенджеров, включая реализацию отсутствующего мониторинга.
- D01–12, в частности≥20 диалогов/сутки на канал и отдельную проверку20 одновременно активных диалогов; число мониторируемых чатов из D10.
- Предложение для счётчиков: считать заявки, подпись единицы явная; общая карточка контакта одна, аккаунтные истории раздельные. Статусы/ожидание менеджера не смешивать с ожиданием клиента. Если нужны счётчики по контактам — скорректировать до RES08.
- Коммерческий GigaChat входит в подготовку, но не покупается автоматически. Ресурсы сервера выбираются по измерению.

Блокеры до соответствующих этапов: тестовый WhatsApp/собеседник; реальные бизнес-настройки и корпус подходящих/неподходящих/сомнительных заявок; разрешённый live список и условия работы с реальными данными; коммерческий credential; off-host backup storage. Они не мешают утвердить план и выполнять независимую разработку.

Дата начала и срок окончания не выдумываются: указанные в договоре G8/G14 — договорные условия, а не автоматически подтверждённый прогноз. После утверждения и RES00 уточнить оставшийся объём и дать прогноз по фактическим результатам transport/monitoring проверки.

## 10. Definition of Done

Релиз готов, когда есть чистый воспроизводимый RC, все обязательные TC01–12 проверены на обоих реальных каналах с GigaChat, устранены блокирующие дефекты, пройдены нагрузка/retention/backup/restore, прежние функции сохранены, есть инструкции и проверенный возврат. Итоговая бизнес-приёмка остаётся за пользователем. Проценты готовности и успешные mock-тесты не заменяют этот результат.
