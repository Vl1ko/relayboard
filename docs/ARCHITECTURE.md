# Архитектура

Поток данных: браузер → API → PostgreSQL/Redis → worker → адаптер платформы. Telegram и WhatsApp вынесены в отдельные bridge-процессы, чтобы их долгоживущие личные сессии не зависели от перезапуска API. MAX-клиент работает внутри worker.

PostgreSQL хранит подключения, адресатов, кампании, вложения, доставки и серверные сессии администратора. Секреты интеграций зашифрованы. Redis/BullMQ хранит отложенные и повторяющиеся задания.

Один fanout создаёт уникальные доставки по паре «адресат + запуск расписания». Далее dispatch отправляет только одну запись и планирует следующую через заданный интервал. Worker имеет глобальную concurrency 1, поэтому параллельные кампании становятся общей очередью.

Статусы доставки: `queued`, `sending`, `sent`, `failed`, `paused`, `stopped`, `skipped`, `unknown`. Временная ошибка повторяется ограниченно; постоянная завершается; при сетевом таймауте используется `unknown`, чтобы автоматический повтор не создал дубль.

Вложения лежат в отдельном persistent volume и доступны API/worker на запись, bridge-процессам — только на чтение. Удаление кампании удаляет связанные файлы.
